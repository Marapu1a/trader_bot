# Bybit Trading Controller — концепция проекта

## Идея

Проект представляет собой **торговый контроллер поверх аккаунта Bybit**, а не отдельную биржу и не клон интерфейса биржи.

**Bybit** остается:

- источником истины по рынку
- источником истины по балансу
- источником истины по позициям, ордерам и исполнениям

**Наше приложение**:

- подключается к аккаунту Bybit
- получает рыночные и приватные данные
- нормализует и хранит локальное состояние
- позволяет выполнять торговые действия
- добавляет поверх биржи собственную логику, проверки и автоматизацию

Ключевая идея: приложение не должно действовать "по памяти" или "по исходным параметрам входа".  
Перед любым действием оно обязано сверять **актуальное состояние рынка и аккаунта**.

---

## Цель первой версии

Построить не "бота со стратегией", а **устойчивую торговую платформу v1**, которая умеет:

- подключаться к Bybit
- видеть текущее состояние аккаунта
- видеть доступные рыночные инструменты
- выставлять и снимать ордера
- читать позиции и исполнения
- безопасно работать в ручном, полуавтоматическом и автоматическом режимах
- служить базой для будущих стратегий

---

## Что это НЕ такое

Проект на старте **не является**:

- HFT-системой
- платформой для микросекундной торговли
- мультибиржевым терминалом
- копией Bybit UI
- системой с несколькими стратегиями одновременно
- ML/AI-движком
- полностью автономным "граалем"

---

## Основная логика

Bybit уже умеет:

- хранить баланс
- вести позиции
- вести ордера
- исполнять сделки
- отдавать цены, свечи, стакан и прочие рыночные данные

Наше приложение нужно для того, чтобы:

- иметь собственную нормализованную модель состояния
- выполнять дополнительные проверки перед действием
- избегать конфликтов состояния
- хранить правила управления
- переводить рыночные события в решения
- исполнять действия вручную, полуавтоматически или автоматически

---

## Режимы работы

### 1. Manual

Пользователь вручную инициирует действия, приложение только:

- показывает текущее состояние
- выполняет проверки
- отправляет команду на биржу
- подтверждает результат

### 2. Semi-auto

Приложение само обнаруживает условия или сигналы, но:

- либо предлагает действие пользователю
- либо выполняет только заранее разрешенные сценарии

### 3. Auto

Приложение самостоятельно:

- отслеживает условия
- принимает решение
- выполняет действия
- контролирует ограничения риска и состояния

---

## Ключевой принцип безопасности

Любое действие допускается **только после сверки актуального состояния**.

Примеры того, что приложение обязано проверять:

- есть ли уже открытая позиция
- есть ли уже активный ордер
- нет ли конфликта между ордером и позицией
- нет ли частичного исполнения, которое изменило состояние
- не было ли ручного вмешательства со стороны пользователя
- не нарушены ли ограничения риска
- не устарели ли локальные данные

Если состояние неоднозначное или конфликтное, приложение должно:

- **ничего не делать**
- зафиксировать конфликт в логах
- ждать повторной синхронизации или ручного решения

---

## Почему это важно

Главная угроза на старте — не рынок сам по себе, а ошибки управления состоянием:

- двойные ордера
- потерянные fills
- устаревший state после реконнекта
- конфликт между локальным состоянием и реальным состоянием биржи
- действия "поверх" уже измененной позиции

Поэтому первая задача проекта — не стратегия, а **надежное управление состоянием**.

---

## Первая практическая цель

Сначала нужно "сесть в кабину крана и проверить рычаги".

То есть до любой стратегии приложение должно уметь:

- подключиться к market WebSocket
- подключиться к private WebSocket
- получать данные через REST для сверки и восстановления
- видеть актуальный баланс
- видеть открытые позиции
- видеть открытые ордера
- видеть последние исполнения
- ставить лимитный ордер
- снимать ордер
- закрывать позицию
- корректно обновлять локальное состояние после каждого события

---

## Источник истины

Источник истины — **Bybit**.

Локальное состояние приложения — это:

- рабочая проекция состояния аккаунта
- слой нормализации
- слой принятия решений

Локальное состояние не должно считаться окончательной истиной без сверки с биржей.

## Основные сущности системы

### Рыночные данные

- instruments
- ticker / mark price / bid / ask
- candles (kline)
- volume
- order book (опционально, позже)

### Аккаунт

- balance
- wallet
- open positions
- open orders
- executions / fills
- leverage / margin info

### Торговые действия

- place order
- amend order
- cancel order
- cancel all orders
- close position
- set stop loss
- set take profit
- reduce position

### Внутренние сущности

- local state store
- action executor
- risk guard
- decision engine
- rule / trigger / condition / strategy

---

## Основные модули проекта

### Exchange layer

Отвечает за интеграцию с Bybit:

- REST client
- public WebSocket client
- private WebSocket client
- форматирование и нормализация ответов биржи

### State layer

Отвечает за локальное состояние:

- account state
- market state
- order state
- position state
- state reconciliation

### Trading layer

Отвечает за торговые действия:

- place / amend / cancel
- close / reduce
- проверка допустимости действия
- идемпотентность команд

### Rules layer

Отвечает за пользовательскую и системную логику:

- guards
- triggers
- conditions
- стратегии
- автоматические сценарии

### Application layer

Отвечает за режимы работы и оркестрацию:

- manual mode
- semi-auto mode
- auto mode
- команды управления
- логирование решений

## Что должно быть в первой итерации

Первая итерация не должна включать стратегию.  
Нужно реализовать только базовый каркас управления.

### Обязательный минимум v0/v1:

- подключение к Bybit API
- чтение рыночных данных
- чтение приватных данных аккаунта
- локальное хранение состояния
- ручные торговые действия
- базовые проверки перед действием
- устойчивость к реконнекту
- логирование событий и действий

---

## Что пока НЕ делаем

На раннем этапе не включаем:

- стратегии и паттерны
- торговлю по сигналам
- машинное обучение
- сложные risk-модели
- опционы и хеджи
- мультибиржевую поддержку
- веб-панель "на полпроекта"
- Telegram-бота
- многопользовательский режим

Все это можно добавлять только после того, как базовый контур станет надежным.

## План развития по этапам

### Этап 1. Infrastructure / Cockpit

Цель:

- увидеть рынок
- увидеть аккаунт
- уметь дергать основные "рычаги"

Результат:

- рабочий торговый контроллер без стратегии

### Этап 2. Safety / State Integrity

Цель:

- убедиться, что система корректно переживает:
  - реконнекты
  - частичные исполнения
  - ручные действия пользователя
  - конфликтные состояния

Результат:

- устойчивая state machine

### Этап 3. Semi-auto Rules

Цель:

- добавить простые проверочные сценарии
- сначала без реальной торговли или с ручным подтверждением

Результат:

- полуавтоматический режим

### Этап 4. Strategy Layer

Цель:

- начать подключать стратегии поверх готовой инфраструктуры

Результат:

- первая автоматизированная торговая логика

---

## Требования к качеству реализации

Система должна быть:

- модульной
- расширяемой
- предсказуемой
- устойчивой к грязным состояниям
- удобной для ручного контроля
- пригодной для постепенного наращивания логики

---

## Важный принцип разработки

Работа идет **маленькими итерациями**.

Подход:

1. формулируем маленькую задачу
2. реализуем
3. проверяем руками
4. убеждаемся, что состояние системы корректно
5. только потом двигаемся дальше

Никаких больших прыжков вперед.  
Сначала инфраструктура, потом логика, потом стратегия.

## Краткая формулировка проекта

**Bybit Trading Controller** — это TypeScript-приложение, которое подключается к аккаунту Bybit и выступает как надстройка над биржей: читает рынок и состояние аккаунта, управляет ордерами и позициями, а также позволяет добавлять поверх биржевых функций собственные проверки, правила, полуавтоматические и автоматические торговые сценарии.
