# Ответ ChatGPT — текущая редакция

Дата: 2026-11-03. Ревью снимка `11a976be811c3a793cf4fbc1ec53290c806998aa`, ответ на [CHATGPT_REQUEST.md](CHATGPT_REQUEST.md).

## Вердикт

Hummingbot подходит как инфраструктура: BinanceExchange, Clock, tracking, REST/WS, торговые ограничения. Но **Grid Strike/GridExecutor в этом снимке не реализует согласованную Spot Grid**. Его нельзя превратить в нужный продукт только YAML-настройками или тонким controller: различаются цены закрытия, стартовый портфель, частичные исполнения и выход за диапазон.

Рекомендую сохранить коннектор и общую инфраструктуру, сделать небольшой проектный SpotGridExecutor/планировщик и тонкий runner. Не переписывать биржевой клиент; не превращать направленный GridExecutor в класс с десятком несовместимых режимов. До Telegram сначала закрыть корректность остановки и неизвестного результата отправки. Полное автоматическое восстановление можно отложить; запрет новых ордеров при неопределённости — нельзя.

Это инженерные предложения, не изменение согласованных требований и не разрешение запускать торговлю или менять VPS. В этой итерации изменён только этот ответ.

## Findings по приоритетам

### P0. Штатный stop может продать активы

**Доказательство по коду.** Цепочка:
`cli/commands/stop.py` → SIGTERM → `cli/engine.py:_serve` → `client/command/stop_command.py:stop_loop` → `strategy/strategy_v2_base.py:on_stop` → `executor_orchestrator.py:393–412` → `executor.early_stop()`.

У GridExecutor аргумент `keep_position=False` по умолчанию (267–275), конфигурационное `config.keep_position` здесь не читается. Затем `control_shutdown_process` / `control_close_order` доходят до `place_close_order_and_cancel_open_orders` (639–660), создающего MARKET для остатка.

**Сценарий:** BUY уже исполнен, SELL ещё нет, config.keep_position=true, пользователь вызывает hbot stop. Возможна рыночная продажа, хотя прямой вызов early_stop(True) в пробе работал правильно.

Также в v2_with_controllers есть StopExecutorAction без явного keep_position. А CLI сообщает об исчезновении процесса; это не доказательство биржевого завершения: engine ловит ошибки stop_loop, пишет running=false и убирает PID.

**Изменение:** проектная операция stop_run должна сначала сохранять STOPPING и блокировать create, отключать controller/очередь команд, затем явно выбирать сохранение активов. Все входы — Telegram, SIGTERM, ручная команда — идут через неё. Не менять глобальный default всех upstream-executors: у них иная семантика. STОPPED только после REST-сверки всех собственных заявок и исполнений. Таймаут означает STOPPING/RECONCILIATION_REQUIRED, а не успех.

**Приёмка:** filled BUY + pending SELL; stop через реальную пользовательскую цепочку; после запроса stop ни одного нового торгового POST, только отмены/чтение; конечные статусы и остатки подтверждены, повторный stop идемпотентен.

### P0. Выход за диапазон ликвидирует/завершает сетку вместо паузы

**Доказательство:** `grid_executor.py:569–599`. Для BUY `mid_price > end_price` безусловно вызывает TAKE_PROFIT; config.keep_position учитывается только в ветке limit_price. Отключение SL/time-limit/trailing и limit_price=0 не отключает этот выход. `tools/testnet_preflight.py` его пропускает.

После завершения `GridStrike.determine_executor_actions` снова создаёт executor, когда нет активных и цена внутри диапазона. Это новый executor, не продолжение прежнего состояния.

**Изменение:** отдельное состояние OUT_OF_RANGE того же run. Обрабатывать fills/cancels и сохранять намерения продолжать; не создавать новые ордера и не отменять старые только из-за пересечения границы. При возврате — reconcile, затем разрешить create. Нельзя просто перестать вызывать весь control_task: тогда замрёт и учёт. Ошибка/отсутствие свежей цены также блокирует новые заявки.

**Приёмка:** выход с обеих сторон, fill во время выхода, возврат; run ID и стартовая закупка не меняются, заявки не дублируются. Stop во время выхода навсегда запрещает автоматическое возобновление этого run.

### P0. Частичный fill исчезает из учёта уровня при отмене

**Доказательство:** `grid_executor.py:786–805` сбрасывает active_open_order/active_close_order на событии отмены, сохраняя только ID в _canceled_orders. `update_position_metrics:829–864` считает позицию только по OPEN_ORDER_FILLED/CLOSE_ORDER_PLACED, использует исходный amount и не вычитает частично исполненный обычный close-order.

Кроме того, open_liquidity_placed/close_liquidity_placed учитывают только ордера с executed_amount_base == 0. Частично исполненный **ещё открытый** ордер становится нулевой «ликвидностью» для условия завершения в control_shutdown_process.

**Сценарии:** купить 0.4 из 1 и отменить остаток → уровень становится NOT_ACTIVE, приобретённые 0.4 не представлены позицией executor. Продать 0.4 из купленного 1 и отменить SELL → reset_close_order возвращает исходный BUY; следующий SELL может вновь запросить полный объём. При наличии чужого BTC на аккаунте обычная проверка баланса не защищает бюджет запуска.

Это дефекты модели executor; не утверждение, что биржа или глобальный recorder потеряли сделку. Гонки реальных событий нужно воспроизвести отдельно.

**Изменение:** остаток уровня = сумма подтверждённых fills с учётом комиссии в base, а не ссылка на последний ордер. Terminal status и accumulated fills хранить отдельно; отмена не обнуляет исполнение. Ждать терминальности всех ордеров, не денежного proxy. Частичный fill + cancel требует явной политики дальнейшей торговли; до её согласования безопасно заблокировать новые действия и показать остаток.

### P0. Неоднозначный POST может превратиться в новый ордер

**Доказательство цепочки:** `binance_exchange.py:_place_order:171–211` отдельно распознаёт только конкретный текст 503. Остальные исключения доходят в `ExchangePyBase._create_order:461–476` → _on_order_failure → FAILED (519–532). GridExecutor.process_order_failed_event (807–827) освобождает уровень для следующей отправки с новым ID.

**Сценарий для воспроизведения:** биржа приняла POST, ответ потерян, WS задержан. До получения подтверждения стратегия считает попытку неудачной и может создать замену. Это не обязательно HTTP-retry того же POST; это повтор торгового решения. Ветка по коду подтверждена, end-to-end дубль пока гипотеза, требуется fault-injection.

**Изменение:** персистентное намерение до сетевой отправки; UNKNOWN не равен FAILED. При неизвестном исходе блокировать повтор уровня и сверять по исходному clientOrderId. Один ответ «не найден» сразу после таймаута не считать достаточным доказательством отсутствия заявки. Срок сверки конечен; по исчерпании — ручное вмешательство, без автоматической замены.

Официальная документация Binance прямо указывает: -1007 может означать неизвестный исход исполнения; при отсутствии события нужна проверка статуса [1].

### P1. Расчёт уровней падает и может превысить выделенный бюджет

**Доказательство + изолированное воспроизведение:** `_generate_grid_levels:121–178`.
- start=100, end=100.01, spread=0.001, mid=100, tick=0.01, budget=100: max_levels_by_step=0, n_levels=0, деление на price*n_levels до max(1,n_levels) → DivisionByZero. Валидатор разрешает такой диапазон.
- budget=1, min_order_amount_quote=5, mid=100, base step=0.001: max_possible_levels=0, но создаётся уровень на 5.300. При наличии денег на аккаунте это превышает именно бюджет запуска.
- float используется для округлений и распределения. Конкретный сбой на границе tick/step здесь не воспроизводился; риск требует граничного теста, а не общего заявления «Decimal везде».

**Изменение:** невозможная сетка должна отклоняться с минимально необходимым бюджетом/причиной. Не увеличивать сумму и не уменьшать запрошенное N молча. Decimal, явное ROUND_FLOOR/CEILING, валидация каждой конечной цены и количества, суммы резервов и уникальности уровней. Для геометрии фиксировать precision и округлять в tick один раз, затем проверять коллизии. Фильтры проверять по exchangeInfo [2].

### P1. max_open_orders не ограничивает размер следующего batch

**Доказательство + воспроизведение:** `get_open_orders_to_create:487–500` проверяет текущее количество, затем берёт [:max_orders_per_batch], не свободные места. При active=1, max=2, batch=5 возвращает 5 уровней. None также означает весь список.

Минимальное исправление: cap = max_open_orders - n_open_orders; batch = cap при None, иначе min(cap, configured_batch). Приёмка: 0/1/2 активных, batch=1/5/None; отдельно pending submissions входят в лимит. Этот upstream-лимит касается opening orders, а не суммы BUY+SELL: общий лимит продукта определить отдельно.

### P1. Цены направленного GridExecutor не соответствуют соседним фиксированным границам

**Доказательство:** `get_take_profit_price:419–420` использует level.price*(1±take_profit). Для арифметических 100/120/140 единый процент 20% даёт 120 и 144, не 120 и 140. _get_open_order_candidate и _get_close_order_candidate дополнительно двигают пересекающие рынок цены к bid/ask с safe_extra_spread. Верхний BUY-уровень может получить TP выше end_price.

coerce_tp_to_step не исправляет постоянную арифметическую разницу. Ни N, ни геометрии, ни распределения стартовых base/quote здесь нет. Controller создаёт направленные одинаковые entry-уровни, а не двухсторонний портфель.

**Решение:** заранее рассчитанные фиксированные boundary IDs и interval IDs; явный соседний target, отдельное состояние инвентаря. Если фиксированный maker-ордер сейчас пересекает рынок, ждать/пересчитать допустимое действие согласно принятому правилу, а не незаметно менять его цену. Политику стартового пустого уровня, цены ровно на границе и стартовой закупки подтвердить примерами с владельцем.

### P1. Комиссия в base и бюджет запуска не защищены настройками по умолчанию

**Доказательство:** `_get_close_order_candidate:447–477` вычитает base fee только при deduct_base_fees=true; default false, GridStrike этот флаг не прокидывает. При покупке 1 с комиссией 0.001 base нужно учитывать чистые 0.999; свободный сторонний base на аккаунте не должен покрывать недостачу запуска.

_open_fee_in_base — общий флаг executor, не надёжный ledger комиссии каждого fill. Не ставлю диагноз численному PnL без отдельного примера: требуется проверка комиссий в base/quote/третьем активе, MARKET-price против фактического executed_quote и отсутствия двойного списания.

### P2. self.step сбрасывается после расчёта

**Доказательство:** __init__ вызывает _generate_grid_levels на строке 55, затем присваивает self.step=0 на 63. Уже записанные GridLevel.take_profit от этого не обнуляются; не преувеличивать эффект. Перенести инициализацию перед генерацией либо убрать последующий reset; проверить итоговый step и TP отдельно.

Ещё небольшая неточность: 1.05 подписано как 20% margin. Исправить комментарий на 5%, не менять торговое значение без причины.

## Совместимость с требованиями

| Требование | В текущем upstream | Минимальное проектное решение |
|---|---|---|
| Binance Spot/Testnet, REST/WS | Реальный коннектор и прогоны есть | Сохранить; добавить UNKNOWN/reconcile на проверенной границе |
| Ровно N интервалов | Число уровней выводится из spread/бюджета | Планировщик N+1 границ, отказ при невозможности |

| Начальные BUY снизу / SELL сверху | Направленные entry→exit | План портфеля и отдельная одноразовая bootstrap-операция |
| Собственный бюджет | Есть конфигурационная сумма, баланс аккаунта не равен ledger запуска | Резервы base/quote/fee по run |
| Partial fills и комиссии | События коннектора есть; модель уровня недостаточна | Fill ledger + остатки уровня |

| Stop без конвертации | Прямой early_stop(True) работает в ограниченной пробе | Один stop_run для всех входов, terminal reconciliation |
| История/восстановление | Recorder/orchestrator сохраняют данные | Сначала fail-closed restart; автоматический resume позднее |
| Telegram | Ещё нет | Команды к одному runner, а не второй исполнитель |

## Пробы: что действительно доказано

TESTNET_GRID_CHECK показывает две отменённые заявки без fills и неизменные балансы. TESTNET_GRID_HOLD_CHECK показывает BUY, отменённый неисполненный SELL и сохранённый base. В этих JSON нет признака fallback_cancel_ids или executor_stop_timeout. Нельзя утверждать, что конкретно эти прогоны были спасены cleanup; проблема — в критерии будущих прогонов.

В `tools/testnet_grid_check.py`:
1. Таймаут executor приводит к executor.stop(), после чего ручной REST cleanup может отменить ордера, а passed всё равно стать true. Разделить strategy_passed и cleanup_succeeded; fallback/timeout всегда проваливает штатный stop-тест.
2. Обычный passed проверяет только непустой набор terminal CANCELED/FILLED. Он не требует двух заявок, нулевых fills и сохранения баланса, заявленных для maker-smoke. Принимать по сценарию, не универсальным «все terminal».
3. REPORT orders дополняется **после** connector.buy/sell. Для устойчивого runner это не journal-before-send. Отдельная ручная order-проба заранее сохраняет ID — правильнее.
4. EventLogger не маркирует источник. Created/Cancelled/Filled могли быть порождены обработкой REST/поллингом, не только private WS. Для доказательства WS отмечать безопасные поля executionReport на входе user stream и коррелировать clientOrderId/orderId/trade ID. Не сохранять raw authentication payload.
5. Напротив, testnet_order_check явно ждёт executionReport через ws.receive_json: он доказывает WS-доставку NEW/CANCELED своей заявки.
6. Если finally делает passed=true после ошибки основного тела, итоговый файл способен содержать passed=true вместе с error_type. Инициализировать результат как false, сохранять раздельно primary_error/cleanup_error и выставлять общий успех только после всего сценария.
7. Глобальное logging.disable(CRITICAL) прячет диагностику. Лучше локальный sanitization и allowlist событий/полей, сохраняя тип ошибки и стадию.
8. BoundedStrategy.stopping запрещает новые ордера как дополнительный предохранитель пробы. Это полезно, но ещё не реализация штатного stop продукта. Не использовать Python assert как единственную защиту будущего сервиса: -O его отключает.

preflight должен прямо сообщать, что текущий GridExecutor не удовлетворяет no-liquidation при выходе вверх. Одних флагов YAML недостаточно.

## Архитектурное решение и roadmap

**Выбор:** один Python-процесс, один торговый runner, один сериализованный поток решений; Telegram вызывает его методы через очередь. BinanceExchange/Clock и существующие типы/трекер сохраняем. Проектный planner/executor хранит состояние именно сетки. Копирование BoundedStrategy целиком в production не предлагаю: нужен нормальный lifecycle, journal и обработка ошибок.

CLI экономит старт процесса и готовый status, но сейчас stop имеет неверную семантику, status не является отчётом run, а конфигурация направленного controller не отражает форму продукта. Если оставлять CLI как внешний транспорт, сначала исправить те же торговые контракты; сам по себе subprocess их не решает. Для одного бота прямой runner проще. Выбор не требует отдельного HTTP-сервера или микросервисов.

| Этап | Работа и зависимости | Критерий готовности |
|---|---|---|
| 1. Корректные границы исполнения | Исправить критерии probes; тесты stop/partial/unknown; определить проектный stop и сверку | Нельзя получить PASS после fallback; при UNKNOWN нет повторного create; частичный fill сохранён |
| 2. План и минимальный SpotGridExecutor | После фиксации стартовых правил: N, распределение, inventory, range-state, ledger | Числовые fixtures и сценарии проходят; цена всегда выбранная граница; бюджет соблюдён |
| 3. Ограниченный Testnet | Journal и stop из этапов 1–2; реальные fills и сверка | buy→sell→новый ID того же уровня либо честный INCONCLUSIVE; отсутствие чужих отмен |
| 4. Telegram-демо | Только после рабочего runner: allowlist user ID, preview, confirm, status, stop, уведомления | Двойное нажатие не дублирует run; показ остатка и незавершённой остановки; один процесс |
| 5. После обратной связи | Полный autoresume, уменьшение зависимостей, дополнительные рынки | Отдельные критерии, не смешивать с текущим демо |

До демо хранить: run ID, schema version, immutable config/plan/hash, состояние run и stop intent; выделенные base/quote, bootstrap status; намерения с clientOrderId **до отправки**, side/price/qty/level/generation; exchangeOrderId и terminal/unknown status; fills с уникальным ключом биржа+symbol+trade ID, количеством/ценой/комиссией/её активом; резервы и checkpoint сверки. Денежные значения — Decimal-строки. Для этого достаточно SQLite и транзакций, без распределённых очередей.

Рестарт пока может входить в RECOVERY_REQUIRED: получить блокировку единственного процесса, найти старые заявки, сверить, показать состояние; **не запускать новую сетку автоматически**. Автоматическое продолжение после аварии, сложную аналитику, multi-user, веб-панель, Futures и массовую чистку зависимостей отложить.

## Следующий сетевой прогон и offline-тесты

Нельзя гарантировать прибыльную maker-пару на живом Testnet за конечное время без гарантии движения рынка. Не подменять это обещание торговлей с собственными заявками.

Предлагаю два раздельных сценария:
- **Настоящая сеточная пара:** одна разрешённая позиция/уровень, минимальный валидный номинал с жёстким общим cap, фиксированные соседние BUY/SELL, дедлайн например 180 секунд. Зафиксировать оба fill и комиссии, затем ровно один новый BUY того же level/generation+1, отменить его через stop_run. При отсутствии рыночного движения — INCONCLUSIVE, корректная остановка с сохранением приобретённого base. Нельзя при timeout принудительно продавать, чтобы «закрыть цикл».
- **Детерминированный транспортный smoke:** отдельно обозначенная тестовая конфигурация с taker BUY и taker SELL в пределах малого лимита и доступной внешней ликвидности, без собственных встречных заявок; затем проверить создание повторного уровня. Это проверяет доставку/учёт/lifecycle, **не maker-стратегию, соседние цены или прибыльность**. Только после исправления остатка/комиссии и явного отделения тестового режима от продукта; сетевые отказы всё равно дают FAIL/INCONCLUSIVE, а не гарантированный успех.

Для сеточной семантики основной воспроизводимый тест — scripted fake exchange, который исполняет заявки и события, а не monkeypatch внутренних счетчиков:
1. BUY 1, fills 0.4+0.6, дубликат одного trade ID: итог 1, ровно одно дальнейшее действие.
2. BUY partial 0.4 → cancel → поздний fill 0.1: после reconcile остаток 0.5, не 0/1.
3. BUY 1 → SELL partial 0.4 → cancel: остаток 0.6 минус применимые комиссии, не новая продажа 1.
4. POST принят → timeout → задержанный WS/REST: один исходный ID и одна биржевая заявка, ноль повторных create до разрешения UNKNOWN.
5. Stop одновременно с fill и возвратом в диапазон: stop имеет приоритет; остаток сохранён, create отсутствует.
6. Комиссия в base/quote/третьем активе; чужой BTC на аккаунте: он не расходуется.
7. Перезапуск после journal intent, после принятия POST и до локального ack: RECOVERY_REQUIRED, новая bootstrap не выполняется.
8. Два уровня завершаются за один tick: оба обработаны ровно один раз. В update_grid_levels есть удаление элементов из перебираемого списка COMPLETE — проверить задержку второго уровня и заменить проходом по копии при подтверждении.
