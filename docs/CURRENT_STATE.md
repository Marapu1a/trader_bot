# Состояние проекта — 2026-11-03

Этот файл — краткая точка входа в фактическое состояние. Требования описаны в GRID_BOT_SPEC.md; предложения внешнего ChatGPT обсуждаем, а не принимаем автоматически.

## Что зафиксировано

- Основа: Hummingbot, upstream commit `9af100d6822da7d2d0291a906c730ef172284ee2`, Apache-2.0. Импортирован снимок исходников; прежняя Git-история и origin сохранены.
- Первая цель: Spot Binance, один активный бот, управление через Telegram. Futures нужен позднее; сейчас не реализуем параллельно.
- Интерфейс и поведение ориентированы на биржевой grid: пара, диапазон, количество сеток, бюджет. Grid Strike ещё не равен этому продукту.
- Ручная остановка отменяет заявки своего запуска и сохраняет оба актива. Никакой обязательной продажи остатка.
- Выход за диапазон: уведомление, без ликвидации. Возврат: продолжение той же сетки, без повторной стартовой покупки.
- Изменение параметров: завершение прежнего запуска и новый запуск с сохранением истории.
- Порядок: Testnet → простой Telegram → показ заказчику → уточнение требований → дальнейшее сокращение ядра и отказоустойчивость.

## Что сделано и проверено

1. Прежний TypeScript-каркас архивирован вне репозитория: `D:\bots\trader_bot_archive_20261103`; там же Git bundle и удалённые upstream-примеры с манифестом. Первая чистка затронула 61 upstream-файл; общий движок, коннекторы и тесты пока сохранены.
2. Добавлен домен `binance_testnet`: отдельные REST, market WS и private WS адреса, регистрация ключей, отказ для неизвестного домена. Боевые адреса не являются fallback для Testnet.
3. Отдельный пользователь и Python 3.12.16 на тестовом VPS, без WSL/Docker и изменения соседних сервисов. Собраны 61 Cython/C++ расширение, CLI запускается. Параллелизм сборки управляется HBOT_BUILD_JOBS.
4. Локально прошли 5 endpoint-тестов. На VPS — 46 выбранных тестов Binance и GridExecutor, 7 предупреждений upstream. Это не весь suite.
5. Подписанное чтение аккаунта и приватная WS-подписка: HTTP/status 200.
6. Одна ручная API-заявка: NEW → CANCELED, события получены, исполнений нет. `TESTNET_ORDER_CHECK.json`.
7. Настоящие BinanceExchange + GridExecutor + Clock: maker-сетка создала две заявки, обе отменены, баланс сохранён. `TESTNET_GRID_CHECK.json`.
8. Отдельный сценарий с MARKET-входом для быстрой проверки исполнения: куплено 0.00014 тестового BTC, GridExecutor создал LIMIT_MAKER-продажу. При `early_stop(keep_position=True)` продажа отменена, BTC сохранён, статус POSITION_HOLD. `TESTNET_GRID_HOLD_CHECK.json`.

Пункты 7–8 выполнены через небольшой адаптер интерфейса стратегии в tools/testnet_grid_check.py, без CLI/controller/Telegram. Это настоящая биржа Testnet и настоящий executor, но не готовый пользовательский запуск. Рыночный вход во втором сценарии — тестовый приём, не принятое правило продукта.

## Что ещё НЕ доказано

- Завершённая пара покупки/продажи и повторная постановка уровня; учёт комиссий и прибыли.
- Частичные исполнения, отмена одновременно с исполнением, timeout с неизвестным исходом POST.
- Выход/возврат в диапазон по нашим правилам.
- Рестарт, восстановление заявок и исключение дубликатов.
- Поведение штатного CLI/controller stop: наличие keep_position в YAML не гарантирует нужный аргумент при остановке.
- Точное количество интервалов, арифметическая/геометрическая сетка, стартовое распределение двух активов.
- Telegram UI, авторизация владельца, постоянный сервис и история запусков.
- Полная сборка Docker: Compose оставлен как альтернативный эксперимент, на VPS не используется.

Тестовые процессы остановлены. Последняя проверка оставила купленные тестовые BTC на аккаунте по согласованной логике. Production-торговля не запускалась.

## Следующие шаги и критерии

1. Ревью границы между готовым GridExecutor и требуемой биржевой сеткой. Результат: таблица «требование → upstream → минимальная доработка» и решение о тонком собственном controller/runner.
2. Ограниченный Testnet-прогон buy → sell → повтор уровня; сверка order IDs, количества, комиссий, остатков. Отдельные проверки выхода/возврата и частичных исполнений.
3. Единый stop-путь: запрет новых заявок, отмена только своего запуска, REST-сверка конечных состояний, сохранение активов. Минимальная персистентность ID необходима до длительных запусков.
4. Простой Telegram: разрешённый пользователь, настройка пары/диапазона/бюджета/сетки, подтверждение запуска, статус, stop, уведомления. Один активный запуск. Секреты не принимать в чат.
5. Демонстрация заказчику с явным перечнем ограничений. После согласования — дальнейшее сокращение коннекторов/зависимостей, восстановление, мониторинг и Futures.

Не расширять этот прототип заранее до платформы. Защита от повторных заявок и сохранение активов — часть торговой корректности, а не необязательная будущая оптимизация.
